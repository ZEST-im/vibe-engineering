## PHASE_PMF08 🚧 IN PROGRESS
> 새는 곳 막기 — 조용한 실패를 소리나게 만든다

W35 리뷰의 진단에서 출발한다: 이 제품이 반복 실패하는 방식은 코드 결함이 아니라
**성공한 것처럼 보이는 침묵**이다. 세 번의 수집 중단, 두 번의 공개 유출 — 다섯 번 다
규율은 있었고 검사가 없었다. 그래서 이 Phase 의 산출물은 문서가 아니라 실행되는 장치다.

- **공개 위생 게이트** — 사내 정보가 공개 파일에 들어가면 CI 가 실패한다. 금칙어 목록을
  레포에 적으면 그 목록이 곧 유출이라 **값이 아니라 모양**을 검사한다(대형 수치·사내 소스
  경로·채팅 uid·인사 DB 컬럼). 검사 대상은 git 이 추적하는 파일 — 경계를 코드가 아니라
  git 에게 묻는다. 도입 즉시 수동 점검이 놓친 3건을 잡았다.
- **직접 편집 경로의 동시성** — 규약은 kanban.json 직접 편집을 기본 경로로 정하는데 그
  경로가 서버 경로보다 약했다. 원자적 쓰기만으로는 부족하다: 두 프로세스가 각자 읽고 각자
  쓰면 나중 쪽이 앞의 것을 덮고 같은 번호를 집는다. git 은 이걸 막지 못한다 — 파일의 다른
  위치에 있는 두 태스크를 깨끗이 머지하고, 보드에서 하나가 에러 없이 사라진다. 읽기-수정-쓰기
  전 구간을 잠그는 `scripts/kanban_edit.py` 를 두고 id 발급은 서버 구현을 재사용했다.
  **대조군을 함께 돌린다** — 잠금 없는 같은 작업이 실제로 깨지는 것을 확인해야 통과가
  의미를 갖는다.
- **스킬 선언과 코드의 대조** — 기존 스킬 테스트는 포장(frontmatter·참조 파일·README
  등재)만 봤다. 이제 문서의 curl 엔드포인트가 서버에 라우팅되는지, 문서가 부르는 스크립트와
  플래그가 실재하는지, 설치 파일 목록이 갈라지지 않았는지를 검사한다. **도입하면서 실제
  버그가 나왔다** — 설치 목록이 세 곳에 흩어져 `setup.py` 단독 설치가 수집기를 빠뜨렸고,
  그래서 어떤 머신은 수집기 없이 며칠을 보냈다. 정본 상수 하나로 합쳤다.
- **수집 파이프라인 관측** — 판단 기준을 "기록된 실패"가 아니라 **성공의 부재**로 잡았다.
  실제 고장 세 건은 프로세스가 아예 뜨지 않아 오류를 남길 주체가 없었기 때문이다. 상태
  파일이 없는 것도 stale 로 보고, 성공 뒤 시도가 실패하면 `degraded` 로 구분한다 —
  이걸 ok 로 부르면 잡으려던 침묵이 그대로 된다. 세션 시작 훅은 서버를 경유하지 않고
  파일을 직접 읽는다. 서버가 죽은 것도 알아야 할 상황이라, 경유하면 같이 눈이 먼다.
