2. 잘된 부분

검사가 도입 당일에 저자를 두 번 잡았다

공개 위생 게이트는 자기 도입 커밋에서 칸반 details 에 적힌 사내 모듈명 2건을 잡았다. 아카이브 검사는 이 레포가 52KB 인 것을 잡았고 시키는 대로 정리해 53,666B → 2,190B 가 됐다. 규칙을 만든 사람이 첫 번째로 걸리는 규칙은 실제로 도는 규칙이다.

위반 주입이 자기 테스트 3개가 공허한 것을 드러냈다

  • 예외 시 잠금 해제 — CPython 참조 카운팅이 대신 해줘 finally 를 지워도 통과. 구현이 아니라 성질을 고정한다고 주석에 명시
  • 아카이브를 완료로 세기 — 테스트 데이터가 이미 status=done 이라 다른 경로로 통과. 실제 방어 대상을 추가
  • 설치 목록 일치 — 문자열 개수 세기라 표기만 바뀌어도 깨짐. AST 참조 검사로 교체

셋 다 통과하고 있었다. 주입하지 않았으면 커버리지가 있는 것처럼 남았을 것이다.

증상이 아니라 발급 지점을 고쳤다

중복 프로젝트 키는 중앙에서 4쌍을 합쳐 46.9억 토큰의 이중 계상을 걷어냈지만, 키를 만드는 쪽이 로컬 디렉토리명이라 다음 push 때 되살아난다. git remote 에서 뽑도록 바꿨고, 드리프트는 보고만 하고 자동으로 바꾸지 않는다 — 키를 바꾸면 중앙 이력이 끊기고 되돌릴 수 없다. 이 머신에서 즉시 2건이 잡혔고 그중 하나가 문제의 그 쌍이었다.

스킬 문서의 주장을 코드와 대조하기 시작했다

기존 test_skills.py 10개는 전부 포장(frontmatter·참조 파일·README)을 봤다. 신규 test_skill_claims.py 10개가 문서의 엔드포인트·스크립트·플래그가 실재하는지 본다. 도입하면서 실버그가 나왔다 — 설치 목록이 세 곳에 흩어져 setup.py 단독 설치가 수집기를 빠뜨렸고, 그래서 어떤 머신은 수집기 없이 며칠을 보냈다.

3. 안 된 부분

P1 · 사내 데이터가 공개 레포로 두 번째 유출 (2주 연속 · critical)

제품별 토큰 소비 실수치(65억·82억·55억)와 사내 애플리케이션의 모듈 경로·인증 함수·토큰 저장 위치가 공개 히스토리에 있었다. 공개 단가표로 곱하면 제품별 개발 지출이 역산된다.

정리에 세 단계가 필요했다 — 히스토리 재작성, 머지된 PR 브랜치 삭제, 그리고 레포 삭제·재생성. refs/pull/1/head 는 push 로 지울 수 없기 때문이다. 재작성 도중 filter-repo 가 Codex 체크포인트 ref 를 경고 한 줄로 건너뛴 것도 나중에 밖에서 clone 해서야 발견했다.

W33 의 실명 유출에 이어 두 번째다. 이번엔 게이트를 만들었으므로 세 번째는 다른 형태여야 한다.

P2 · CI 가 네 커밋 동안 빨간 것을 몰랐다 (신규 · high)

f52f87e~8a147a4 가 lint 실패 상태로 들어갔다. 테스트는 3버전 전부 통과하고 ruff 만 실패했는데, 로컬에 ruff 가 없어 "전체 테스트 OK" 가 CI 의 절반만 본 것이었다.

여기에 두 번째 실수가 겹쳤다 — 푸시 후 gh run list 맨 위를 봤는데 그게 아직 이전 커밋의 실행이었다. 초록을 봤지만 내 커밋의 초록이 아니었다.

이 Phase 가 여덟 개의 검사를 만드는 동안, 검사를 돌리는 쪽에 같은 종류의 구멍이 있었다.

P3 · 커버리지가 여전히 측정되지 않는다 (3주 연속 · medium)

W33·W35 초안에 이어 세 번째다. 353개가 무엇을 덮는지 아무도 모른다. 이번 주에 자기 테스트 3개가 공허했던 것을 주입으로 발견했는데, 커버리지 수치가 있었다면 더 싸게 찾았을 수도 있다. e2e 산출물 경로 test_temp/ 도 .gitignore 36행에 그대로다.

P4 · 병렬 세션이 같은 워킹트리를 공유한다 (2주 연속 · high)

다른 세션이 이 세션의 미커밋 작업을 커밋하고 푸시했다(d331893, 18:52). 그 커밋에 W35 리뷰 HTML 이 들어 있었고, 거기 적힌 사내 수치가 그렇게 공개됐다 — P1 의 경로 중 하나가 이것이다. 잠금은 kanban.json 에만 걸었지 워킹트리 전체에는 걸 수 없다.

P5 · 히스토리를 두 번 재작성했다 (신규 · medium)

모두 필요한 조치였지만 대가가 있다. 다른 머신이 ahead 36 / behind 42 로 갈라진 채 방치돼 있었고, 그대로 pull 했으면 스크럽한 내용이 되돌아갔다. 재작성 이후 다른 클론이 어떤 상태인지 추적하는 장치가 없다.

6. 이해도 점검

찾아보지 않고 답할 수 있어야 한다.

  1. 수집 파이프라인 관측에서 "기록된 실패"가 아니라 "성공의 부재"를 보기로 한 이유는? 통과하는 답은 실제 고장 세 건이 왜 오류를 남기지 못했는지를 말해야 한다. 상태 파일이 없는 것을 어떻게 판정하는지도.
  2. kanban_edit.py 가 원자적 쓰기만으로 부족한 이유는? 통과하는 답에는 두 프로세스의 읽기-수정-쓰기가 겹치는 시나리오와, 그것이 어떤 관측된 손상(id 두 개)으로 이어졌는지가 나와야 한다.
  3. 키 드리프트를 발견하고도 자동으로 고치지 않는 이유는? 통과하는 답은 "되돌릴 수 없다"에 그치지 않고, 중앙 집계가 어느 단위로 중복 제거를 하는지까지 설명해야 한다.

CTO 종합 판정

만드는 쪽은 이번 주에 확실히 올라갔다. 여덟 개의 장치가 들어갔고 전부 위반 주입으로 검증됐으며, 자기 테스트가 공허한 것을 스스로 세 번 찾아 고쳤다. 증상이 아니라 발급 지점을 고친 판단, 그리고 "재현됐으니 스킬로 뽑자"가 아니라 "문서로는 안 되니 검사로 바꾸자"로 간 판단은 신입 기준이 아니라 그냥 좋은 판단이다.

그러나 지키는 쪽이 따라오지 못했다. 같은 기간에 사내 데이터가 두 번째로 공개됐고 레포를 지웠다 다시 만들어야 했다. CI 가 네 커밋 동안 빨갰는데 몰랐고, 그 원인은 검사를 만드는 동안 검사를 돌리는 쪽에 같은 구멍을 둔 것이었다.

판정은 여전히 조건부다. 이 레포는 자기 결함을 잘 찾지만, 찾는 장치와 그것을 돌리는 규율 사이의 간격이 계속 사고를 만든다. 종합을 7로 유지하는 이유가 그것이다 — 8은 "그 범위에서 운영 준비가 됐다"는 뜻인데, 자기 CI 상태를 네 커밋 동안 몰랐던 주에 붙일 수 없다.
