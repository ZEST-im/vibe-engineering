## 1. As-is — 문서와 데이터가 갈라진 곳

### 🔴 ① 같은 엔티티가 두 곳에 살고, 읽는 경로가 다르다

task 는 `kanban.json` 과 `vibe-harness/archive/YYYY-MM.json` 에 나뉘어 있다.
**절반이 아카이브에 있다** (1,327 / 2,671 = 49.7%).

이것이 가설이 아닌 이유: **오늘 이 문서를 쓰면서 내가 먼저 틀렸다.** 첫 집계에서
`archive/` 하위 디렉토리를 못 봐 2,671건을 1,344건으로 셌다 — 50% 적게. 스키마 문서에
아카이브의 읽기 경로가 적혀 있지 않고, `kanban.json` 안에 아카이브를 가리키는 키도 없다.
`depends_on` 판정이 *"아카이브된 의존은 done 으로 친다"* 라고 규정돼 있으니
(`task-schema.md:104`) **이 둘을 같이 읽지 않으면 판정이 틀린다.**

### 🔴 ② 스키마 문서가 금지한 것이 데이터의 17% 다

`task-schema.md:52` — *"`created_by` 와 `assigned_to` 는 **사람**을 담는다.
에이전트 이름(`claude`, `codex`, …)이 아니다. 에이전트 귀속은 `runs.json` 의 `agent` 에 있다."*

| 위반 | 건수 |
|---|---|
| `assigned_to = codex` | 209 |
| `created_by = claude` | 143 |
| `created_by = codex` | 70 |
| `assigned_to = claude` | 33 |
| **합계** | **455건 — 2,671 중 17.0%** |

규정은 명확하고 정본 문서에 있다. **검사가 없어서 지켜지지 않았다.**
기여자 집계·비용 귀속이 전부 이 필드를 탄다.

같은 줄이 *"소유자 없는 done 태스크는 기록 버그"* 라고 규정한다.
`assigned_to` 가 빈 done 은 **840건 (31.4%)** 이다.

### 🟡 ⑤ 코드 집합에 통제가 없다

| 필드 | 규약 | 실제 |

### 🟡 ⑥ `review` 라는 이름이 두 가지를 뜻한다

같은 단어가 상태이자 검수 메모다. 에이전트가 "review" 를 읽고 무엇을 가리키는지
알 방법이 없다. 글로서리에서 **필드 쪽 이름을 바꿀 후보**로 표시했다.

- `depends_on` **0건 (0.0%)** — 스키마·판정 코드·순환 검사까지 다 있는데 아무도 안 쓴다.

## 2. 개념 모델 — 업무의 말로

```
     사람 ──소유──▶ Task ──속한다──▶ Phase ──속한다──▶ Project
      │              │  │                                 │
      │              │  └──낳는다──▶ Decision              │
      │              │                                     │
    에이전트 ──수행──▶ Run ──(끊겨 있다, 4.9%)──▶ Task      │
                                                           │
                                          Project ──사본──▶ Snapshot(중앙)
```

| 엔티티 | 업무의 말로 | 근거 |
|---|---|---|
| **Project** | 보드 하나를 가진 레포 | 26개 실재 |
| **Task** | 사람이 하기로 한 일 한 덩어리 | 2,671건 |
| **Decision** | 되돌리기 비싼 선택과 다시 볼 조건 | 253건 |
| **Run** | 에이전트가 한 번 돈 것 — 토큰·모델·시간 | 840건 |
| **Phase** | 일의 묶음. **엔티티가 아니라 Task 의 문자열이다** | 39종 접두어 |
| **사람 / 에이전트** | **엔티티가 아니라 문자열이다** | 아래 ③ |

**엔티티가 아닌 것 둘이 문제의 근원이다.** Phase 와 사람은 개념상 실체인데 저장은
자유 문자열이라 오타와 동의어를 막을 곳이 없다. 다만 **지금 테이블로 승격하지 않는다** —
`00_solution.md` 결정 #3(JSON 유지)이 있고 사용자 1인이다. 대신 글로서리로 이름을 고정하고
검사로 막는다.

## 3. 논리 모델

### 식별

| 엔티티 | 업무상 정체성 | 대리키 | 문제 |
|---|---|---|---|
| Task | (Project, id) | `id` = `{접두어}{번호}` | **보드 안에서만 유일하다.** 전역 유일이 아니다 |
| Decision | (Project, id) | `id` | 같음 |
| Run | `session_id` | 없음 (append-only) | 99.3% 채워짐 — dedup 의 기반 |
| Project | `key` | 디렉토리 경로 | `00_solution.md` 결정 #1 |

`id` 접두어는 **사람+머신** 단위다 (`hgA`=mac-studio, `hgB`=macbook). 번호는 보드별
`next_id` 로 발급하므로 **두 머신이 같은 보드에 동시에 쓰면 번호가 두 번 발급된다** —
`task-schema.md:87` 이 이미 이 성질을 적어 두었다.

### 시간

| 값 | 어떻게 | 규정 |
|---|---|---|
| `created_at` | 생성 시 1회, 이후 불변 | 지켜짐 (92.8%) |
| `started_at` | `in_progress` 로 **처음** 갈 때 | 09-29 에 직접 생성 경로를 고쳤다 |
| `completed_at` | `done` 으로 갈 때. 재개하면 지운다 | 09-29 에 CLI 경로를 합쳐 고쳤다 |
| 표기 | ISO-8601, **KST aware** | 나이브 값을 UTC 로 읽으면 9시간 어긋난다 |

**Task 는 현재 상태만 갖는다. 이력이 없다.** 상태 전이 기록은 어디에도 남지 않는다 —
`task_history` 는 `Do NOT touch` 의 SCOPE_LOCK 이다(의도적으로 안 만든다).
**아카이브는 이력이 아니라 이사다** — 같은 현재 상태가 다른 파일로 옮겨질 뿐이다.

유일한 진짜 이벤트 로그는 **`runs.json`(append-only)** 이고, 그래서 `task_id` 4.9% 가
아픈 것이다 — 이벤트는 있는데 무엇에 대한 이벤트인지가 없다.

### 불변식 — 지금 코드가 지키는 것과 안 지키는 것

| 불변식 | 강제되나 |
|---|---|
| `status` ∈ 5종 | ✅ 코드 |
| `id` 재사용 금지 · `next_id` 단조증가 | ✅ 코드 |
| 사람당 `in_progress` 1개 | ✅ 코드 |
| `done` 이면 `completed_at` 이 있다 | ✅ 09-29 에 닫음 |
| **`created_by`·`assigned_to` 는 사람이다** | ❌ **위반 455건** |
| **`done` 이면 `assigned_to` 가 있다** | ❌ **위반 840건** |
| `depends_on` 에 순환 없음 | ✅ 코드 (단 대상이 0건) |

## 8. 마이그레이션 규칙

지금은 **규칙이 없다.** `version: 1` 은 26개 보드 전부에 있고 아무도 읽지 않는다.
필드 추가는 자유, 제거·개명은 금지(`Do NOT touch`)로 버텨 왔고 실제로 깨진 적은 없다.

**여기서 마이그레이션 체계를 만들지 않는다.** 만들 근거가 없다 — 파일이 JSON 이라
필드 추가에 이주가 필요 없고, 제거·개명은 이미 금지돼 있다. 대신 **그 금지가 지켜지는지를
검사로 옮기는 것**이 값이 있다(아래 9).

한 가지만 규칙으로 적는다: **개명이 필요하면 expand-then-contract** — 새 이름을 추가하고,
읽기를 둘 다 받게 하고, 백필하고, 그 다음에 옛 이름을 버린다. 위 ④ 의 6개 이름을 정리할
때 쓸 순서다.
