## 1. As-is — 실제로 배포된 것

### 배포 단위는 하나인데 **두 데몬이 서로 다른 트리를 돈다**

| 데몬 | 무엇을 실행하나 | 주기 |
|---|---|---|
| `com.vibe-harness.server` | `~/.claude/skills/vibe-harness/server.py` — **설치본** | 상주 (`KeepAlive`, `ThrottleInterval` 5초) |
| `com.vibe-harness.reconcile` | `~/dev-hoarchi/vibe-engineering/scripts/reconcile_runs.py` — **작업트리** | 3시간 (`StartInterval` 10800) |

🟡 **수집기는 체크아웃된 브랜치를 돈다.** 지금 이 트리는 `fix/update-skill-covers-all-skills`
브랜치이고, 3시간마다 launchd 가 그 브랜치의 코드로 토큰을 수집한다. 오늘은 설치본과
내용이 같아서 차이가 없지만, **그건 우연이지 설계가 아니다** — 리베이스 중이거나 반쯤
고친 상태여도 그대로 돈다. `install_reconcile.py` 가 plist 를 그렇게 생성한다.

레포의 `com.vibe-harness.server.plist` 와 설치본의 차이는 `__HOME__` 치환뿐이다 —
**드리프트가 아니라 템플릿이다.** 확인했다.

### 🔴 ② 크래시 루프가 95,251회 돌았고 아무도 몰랐다

`server.log` 에 **`UnboundLocalError` 가 95,251건** 있다. 전부 같은 것이다 —
`main()` 이 배너를 찍을 때 `projects` 가 대입되지 않아 **시작할 때마다 죽었다.**

```
95,251회 × ThrottleInterval 5초 ≈ 132시간 ≈ 5.5일 동안 쉼 없이 재시작
```

**버그 자체는 이미 고쳤다** — `server.py:3281` 에 왜 그랬는지 주석까지 남아 있다
(*"떠 있던 프로세스가 옛 코드로 돌던 동안은 보이지 않았다"*). 고친 것이 문제가 아니다.

**문제는 이것이다: 5.5일짜리 크래시 루프의 유일한 기록이 아무도 안 여는 39MB 로그다.**
`00_solution.md` 가 센 "조용한 실패 7건 중 검사가 잡은 것 0건" 에 **8번째가 여기 있었고,
그것도 못 세고 있었다.** 품질 목표가 "정확성 — 기록이 거짓말하지 않는다" 인 시스템에서
5.5일 동안 서버가 죽어 있었다는 뜻이다.

### 🟡 ③ 로그가 39MB 이고 회전 장치가 없다

| | |
|---|---|
| `server.log` | **39 MB · 666,810줄** · 첫 줄부터 지금까지 전부 보관 |
| `reconcile.log` | 167 KB |
| 회전 설정 | **0건** — logrotate·newsyslog·코드 어디에도 없다 |
| 사는 곳 | `~/.claude/skills/vibe-harness/` — **설치 디렉토리 안** |

설치본 디렉토리가 47MB 인데 **그중 39MB 가 로그다.** 설치물과 런타임 산출물이 같은
디렉토리에 섞여 있다.

### 🟠 ④ 인프라가 없다 — 이건 정상이다

컨테이너 없음 · IaC 없음 · 클라우드 없음 · **런타임 의존성 없음**(표준 라이브러리만).
서버는 `127.0.0.1:4242` 에만 바인딩한다. `vibe-sa` 가 *"인프라 산정 대상이 없다"* 고 한 것은
**이 부분에 한해서는 맞았다.** 아래 §3 의 용량 산정이 짧은 이유다.

## 3. 용량 산정

이 시스템은 **사용자 1인 · 로컬** 이라 전통적 용량 산정(동시접속·req/s·노드 수)이
적용되지 않는다. 실제로 한계에 부딪히는 것은 **파일 크기와 전송 한도** 셋뿐이고,
그 셋만 산수를 보인다.

### ① 세션 시작 비용 — 실제로 관리되는 유일한 성능 제약

```
kanban.json 26개 합계          2,562 KB   [실측]
최대 보드 (codebook_vibe)        354 KB   [실측]
세션마다 읽히는 것 = 그 프로젝트의 kanban.json 1개
  354 KB ÷ 약 3.5 bytes/token  ≈ 101K 토큰   [가정: 한글 혼재 JSON 의 대략치]
```

**가장 민감한 입력은 보드당 live 태스크 수다.** 그래서 월 단위 아카이브가 있다
(이 레포는 live 40건·122KB 에서 경고가 뜬다). 아카이브가 이 제약의 유일한 대응이고,
지금까지 작동해 왔다 — live 1,344 / archive 1,327 로 **정확히 절반을 밀어냈다.**

### ② 스냅샷 전송

```
보드 데이터 전체                 5.5 MB   [실측: kanban 2.5 + archive 2.6 + runs 0.4]
중앙 413 임계값                  (1.25 MB, 5.35 MB] 구간   [실측 09-28]
  → 1.25MB 단건은 통과, 5.35MB 번들은 거부
대응: SNAPSHOT_BUDGET 1,000,000 에서 시작해 막히면 절반씩, 하한 50,000
실측 5,354,178 B · 13 source → 6덩어리로 전부 전송 성공
```

**임계값을 맞히려 하지 않는다** — 중앙이 별개 레포 소유라 바뀔 수 있다.
사다리가 임계값을 몰라도 도는 것이 설계다.

### ③ 디스크

```
transcript 원본        478 MB   [실측]  ← 우리가 안 지운다 (Claude Code 것)
보드 데이터            5.5 MB   [실측]
설치본                  47 MB   [실측]  = 코드 8MB + 로그 39MB
                                          └─ 회전 없음. 이것만 무한히 자란다
```

**증가가 제한되지 않는 것은 로그 하나다.** 5.5일 크래시 루프가 39MB 를 만들었으니
대략 **7 MB/일** 이 상한 근처의 증가율이다. 정상 운영에서는 훨씬 느리지만 **상한이 없다.**

## 4. 실패

| 구성요소 | 실패하면 | 어떻게 감지되나 | 복구 | 걸리는 시간 |
|---|---|---|---|---|
| `server` (상주) | 보드 UI·API 불가 | 🔴 **없다.** launchd 가 조용히 재시작 | `KeepAlive` 자동 | 5초 — **단 고쳐지지 않으면 영원히 루프** |
| `reconcile` (3시간) | 토큰·모델 수집 정지 | 🔴 **없다.** 로그에만 | 다음 주기에 재시도 | 최대 3시간 |
| 중앙 전송 | 스냅샷 적체 | 🟡 `sync-pending.json` 에 쌓인다 (사람이 봐야 앎) | 다음 성공 시 함께 전송 | 무기한 |
| transcript 형식 변경 | 수집이 **조용히 0건** | 🔴 **없다** — `00_solution.md` 위험표 1번 | 사람이 코드 수정 | 미상 |
| 보드 파일 손상 | 그 프로젝트 보드 소실 | 로드 실패 | git 에서 복원 | 분 단위 |
| `sync.json` 소실 | 중앙 동기화 정지 | 전송이 조용히 꺼진다 | **재발급 필요 — 사본이 없다** | 미상 |

**`KeepAlive` 가 위험을 감춘다.** 실패해도 5초 뒤 살아나므로 **밖에서 보면 정상이다.**
95,251회 루프가 그렇게 5.5일 갔다. 이 레포의 판단 기준
*"응답 없는 실패를 만들지 않는다"* 에 정면으로 걸린다.

| | 지금 |
|---|---|

| 메트릭 | 없음 |
| 트레이스 | 없음 |

| 보존 | 무기한 |

🔴 **알림이 하나도 없는 것이 이 문서의 핵심 소견이다.**

`00_solution.md` 의 품질 목표는 *"수집·전송·설치 중 하나가 조용히 멈추면 **다음 세션
시작에 사람이 안다**"* 였다. **지금 그 경로가 존재하지 않는다.** 실패는 전부 로그로
가고, 로그는 아무도 열지 않는다 — 95,251건이 그 증거다.

세션 시작 훅이 이미 돌고 있고 Phase 요약을 찍는다. **거기가 알림이 붙을 자리다** —
새 인프라가 필요 없고, "다음 세션 시작에 안다" 라는 목표의 문자 그대로다.

붙일 것은 품질 목표의 시나리오와 1:1 이어야 한다. CPU 몇 % 가 아니다:

| 알릴 것 | 판정 기준 | 목표의 어느 줄인가 |
|---|---|---|
| 서버가 재시작을 반복한다 | 최근 로그에 같은 예외 N회 이상 | 정확성 — 조용히 멈춤 |
| 수집이 멈췄다 | `runs.json` 최신 `ts` 가 6시간 넘게 옛것 | 정확성 — 조용히 멈춤 |
| 스냅샷이 적체됐다 | `sync-pending.json` 이 비지 않은 채 N시간 | 정확성 — 조용히 멈춤 |
| 설치본이 낡았다 | 설치본과 레포 HEAD 의 해시 불일치 | 위험표 4번 |

**받는 사람은 한 명이다 — 사용자 본인.** 1인 시스템이라 당번 논의는 없지만,
*"받는 사람이 없는 알림은 로그 한 줄이다"* 는 그대로 적용되어 **세션 시작 화면**이
수신처가 된다.

로그 회전도 같이 필요하다. **크기 상한 + 보관 개수**면 충분하다 — 표준 라이브러리
`logging.handlers.RotatingFileHandler` 로 되고, 의존성 0 원칙을 깨지 않는다.

## 9. 비용

**인프라 비용은 0원이다.** 서버 없음 · 클라우드 없음 · 의존성 없음. 개발자 머신에서 돈다.

⚠️ **이 합계를 비용으로 환산하면 안 된다.** Claude 는 캐시 읽기가 지배적이고

**비용이 무엇에 비례하는가**: 세션 수와 세션당 컨텍스트 크기. 그래서 이 레포가 세션 시작
